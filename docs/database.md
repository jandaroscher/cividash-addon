# Database

## The `cividash` database

CiviDash keeps all its state in PostgreSQL: content, users, sessions, cache
and the job queue (`SESSION_DRIVER`, `CACHE_STORE` and `QUEUE_CONNECTION` are
`database`). The add-on runs no database server. It requests a database on
the platform's CloudNativePG cluster through
[`databases.yaml`](../databases.yaml):

| Setting | Value |
| --- | --- |
| Database and role | `cividash` |
| Cluster | The platform's cluster (`embedded: true`), service `postgres-cluster-rw` in the postgres namespace, port 5432 |
| Password | Secret `db-cividash`, key `password` |

CORE's postgres component creates the database and the role. The password is
generated by the secrets component from [`secrets.yaml`](../secrets.yaml):
the Secret `db-cividash` (keys `username` and `password`, 32 characters) is
written to the cividash namespace, where CiviDash reads it, and to the
postgres namespace, where CloudNativePG sets it on the role. Nothing has to
be configured in the environment.

The add-on's values pass the connection to the chart:

| Chart value | Value |
| --- | --- |
| `db.host` | `postgres-cluster-rw.<postgres namespace>.svc.cluster.local` |
| `db.port`, `db.database`, `db.username` | From `databases.yaml` |
| `db.passwordSecret` | Secret `db-cividash`, key `password` |

The chart renders host, port, database and user into the hook Secret
`cividash-db-secret`. The password reaches the containers only as
`DB_PASSWORD` through `secretKeyRef`.

## Network access

The networkpolicies component denies all ingress by default, also in the
postgres namespace. [`networkpolicies.yaml`](../networkpolicies.yaml) adds
the policy `cividash-postgres` there: pods labelled
`app.kubernetes.io/part-of: cividash` of the release `cividash-cividash`
(fpm, queue, scheduler and the migrate and seed Jobs) may reach the
`postgres-cluster` pods on 5432; with Linkerd, the same peers on 4143
([`networkpolicies-linkerd.yaml`](../networkpolicies-linkerd.yaml)). Apply
the networkpolicies component after adding or changing these files.

## Schema migrations

The pre-install and pre-upgrade hook Job `cividash-migrate` runs
`php artisan migrate --force` before the workloads roll out. The image pinned
in [`images.yaml`](../images.yaml) includes `pdo_pgsql`; an image without it
fails with `could not find driver` (see
[Troubleshooting](troubleshooting.md#migrate-or-seed-job-fails-with-could-not-find-driver)).

## Backup and restore

The `cividash` database is part of the platform's PostgreSQL cluster and is
covered by the backup the operator runs for that cluster. To back up or move
CiviDash alone, dump the single database, for example:

```bash
kubectl -n <instanceSlug>-postgres exec postgres-cluster-1 -c postgres -- \
  pg_dump -Fc cividash > cividash.dump
```

A restore needs the `APP_KEY` of the same installation (Secret
`cividash-app-key`, see [Helm chart, APP_KEY](helm-chart.md#app_key)):
encrypted columns and sessions cannot be read with another key. Media are
not in the database, see [Media storage](storage.md#backup).

## Migrating from CIVITAS/CORE 1

CORE 2 has no in-place upgrade. Before the first deployment, create the
Secret `cividash-app-key` with the old `APP_KEY` (see
[Helm chart, APP_KEY](helm-chart.md#app_key)). After the first deployment has
created the empty `cividash` database, restore a dump of the old database
into it as the role `cividash`, for example with
`pg_restore --no-owner --role=cividash -d cividash`, then restart the
CiviDash deployments. Sessions, cache and queue move with the database.

## Uninstall

The database, the role and the Secret `db-cividash` belong to the platform's
postgres and secrets components. Destroying the add-on's release leaves
them in place; remove them by hand if you no longer need the data.
